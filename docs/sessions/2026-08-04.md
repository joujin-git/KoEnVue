## [08:12] 트레이 메뉴 2단 재편 + 용어 정리 — 「플로팅 배지」 → 「한/영 배지」

사용자 질문("배지 9항목 중 커서와 무관한 것 조사")에서 출발해 메뉴 구조 개편까지 이어졌다.

### 조사 결과 — 9항목 전부 배지 전용

트레이 메뉴 「투명도」~「플로팅 배지 숨김」 9항목이 커서 헤일로에 닿는지 확인: **하나도 닿지 않는다.** [CursorOverlay.cs](../../App/UI/CursorOverlay.cs) 가 읽는 config 키를 전수 조사하니 9항목의 키가 **0건**이고, 간접 경로(`HideOverlay` · `DetectionService` 의 `PositionMode` · 드래그 경로)도 전부 배지에서 끝난다. 대응 설정은 커서 쪽에 따로 있다 — `Opacity`↔`CursorHaloOpacity` · `IndicatorScale`↔`CursorOuterRadius` 등 · `ChangeHighlight`↔`CursorChangeHighlight` · `UserHidden`↔`CursorIndicatorEnabled`.

**공유되는 것은 2가지뿐**: 색상 3키(`CursorOverlay.BuildStyle` 이 배지와 같은 값을 읽음)와 `AnimationEnabled`(양쪽 강조의 마스터). 둘 다 이미 메뉴에서 9항목 밖에 있어 **구획 나눔이 코드와 정확히 일치**했다.

### 한 것

**1. 대분류 서브메뉴 2개로 접기** — 최상위 **20줄 → 9줄**. 「한/영 배지 ▸」에 설정 8개, 「커서 헤일로 ▸」에 2개. 부모가 대상을 밝히므로 자식 라벨의 접두를 제거("플로팅 배지 변경 강조" → "전환 강조").

**2. 숨김 토글 2종은 최상위 맨 위로** (사용자 지시) — 접었다면 2단이 됐을 항목이 오히려 1단을 유지한다. 근거도 있다: 좌클릭 순환을 끈 환경에서 **유일한 숨김 해제 경로**라 [User_Guide](../User_Guide.md) 가 이미 「안전망」이라 부르던 항목이다.

**3. 용어 4건 정리** — 「플로팅 배지」→「한/영 배지」(플로팅이 직역이라 뜻이 안 옴) · 「커서 헤일로 표시」→「선명도」(켜고 끄는 스위치로 오해, 실제로는 3종 선택) · 「위치 모드」→「위치 기준」 · 「변경 강조」→「전환 강조」(User_Guide 가 이미 쓰던 이름).

### 왜

- **문서가 이미 증거를 남기고 있었다** — User_Guide 항목표가 "**투명도** | 플로팅 배지 — …" 처럼 설명마다 접두를 붙여야 했다. 라벨만으로 대상이 안 드러난다는 뜻이고, 서브메뉴로 접으면 그 접두가 부모 이름으로 흡수돼 표가 오히려 짧아졌다.
- **「항목 제목 줄」안을 물리친 이유** — 이 앱은 회색 처리(`MF_GRAYED`)를 이미 「지금 못 쓰는 항목」 뜻으로 쓰고 있다(기본 위치 ▸ 초기화). 제목까지 회색이면 두 의미가 충돌하고, 회색을 빼면 눌리지 않는 평범한 항목이 된다.
- **「헤일로」는 남겼다** — 생소하지만 *동심원 + 흰 안개* 라는 생김새를 정확히 가리키는 고유명에 가깝다. 「링」으로 바꾸면 안개가 사라진다. 「플로팅」과 달리 대체가 손해다.
- **개수 표기는 또 낡아 있었다** — [architecture.md](../architecture.md) 가 I18n public 속성을 **43개**라 적었는데 실제는 **70개**(내 추가 2 제외 68). 08-03 의 테스트 baseline 226→236 과 같은 자리다. 릴리즈 절차 때처럼 **값 표기 자체를 제거**하고 세는 명령을 적었다.
- **코드 주석은 일단 남겼다** — 주석이 가리키는 것은 UI 라벨이 아니라 코드 개념(`Overlay` 클래스, 떠 있는 창)이라는 판단. 문서는 전부 통일했다(한 문서 안에서 용어가 섞이는 쪽이 더 나쁘다). **→ 08:25 에 사용자 요청으로 주석까지 통일. 아래 블록 참조.**

### 내가 틀린 수치를 보고했다

앞 블록과 커밋 `d7d4c9b` 에 주석 잔재를 **「약 337곳」**이라 적었는데 **실제는 67곳**이다. 전체 441 회에서 문서 몫을 빼는 식으로 어림한 값을 그대로 보고했고, `.cs` 만 직접 세어 보지 않았다. 판단 자체(주석/문서 경계)는 개수와 무관하지만, **「337곳이라 diff 가 커진다」는 비용 근거를 5배 부풀려 제시**한 셈이라 사용자의 결정 재료가 왜곡됐다. 세는 데 명령 한 줄이면 됐다.

### 일괄 치환은 08-03 의 실패를 피해서

`sed -i` 대신 .NET `File.ReadAllText`/`WriteAllText` + `UTF8Encoding($false)` 로 처리했다. 08-03 의 `config.json` 개명 때 `sed` 가 줄바꿈까지 바꿔 **98개 파일이 변경으로 뜨는데 실제 내용 변경은 48개**였던 일이 있었다. 이번엔 사전에 인코딩(UTF-8 **BOM 없음** · LF)을 확인하고 원본 바이트 형태를 유지했다.

**검증**: `git diff --numstat` 으로 `.cs` **추가 67 / 삭제 67** — 1:1 치환. 변경 파일 중 **diff 가 비어 있는(=줄바꿈만 바뀐) 파일 0개**. `bin`/`obj` 는 스캔에서 제외(123파일 스캔 → 28파일 변경).

## [08:45] 메뉴 핸들 누수 실측 — ✅ 누수 없음

2단 중첩이 된 뒤 `DestroyMenu` 가 서브메뉴 8개를 제대로 회수하는지 확인했다. **HMENU 는 USER 오브젝트**라 `GetGuiResources(hProcess, GR_USEROBJECTS)` 로 직접 셀 수 있다.

### 정적 검증 (즉시)

`CreatePopupMenu` **9회** = `MF_POPUP` 부착 **8회** + 최상위 1개(`DestroyMenu` 대상). 트리는 `hMenu` ← 대분류 2, `hBadgeMenu` ← 5, `hCursorMenu` ← 1 로 **고아가 될 서브메뉴 0**. 조기 `return` 2개(`_initialized` · `RejectReentry`)는 **첫 `CreatePopupMenu` 보다 앞**에 있고 `throw` 도 없어 생성 후 이탈 경로가 없다.

### 런타임 측정

측정 자체가 두 번 막혔고, 그 과정이 기록할 값이 있다.

1. **앱이 관리자 권한으로 self-relaunch 해 핸들 조회가 전부 거부됐다.** publish 폴더 `koenvue_config.json` 에 `admin_elevation: true` 가 남아 있었다(08-03 실기 C-1 에서 켠 값). 일반 권한 셸에서는 elevated 프로세스의 `Handle`·`Path` 가 **빈 값으로 조용히 반환**된다 — 예외가 아니라 빈 값이라 원인을 오해하기 쉽다.
2. 해결: exe 를 임시 폴더에 **복사해서 실행**. config 가 없으니 `admin_elevation` 이 기본값(false)이라 일반 권한으로 뜬다. **사용자 설정·포터블본을 건드리지 않는다.**

**계측기 양성 대조부터 세웠다** — 「안 늘었다」는 부정 관측은 계측기가 죽어 있어도 똑같이 나온다. 메뉴를 열 때 **USER 가 +13 튀는 것**을 먼저 확인해 계측기가 HMENU 에 반응함을 입증한 뒤에야 누수 판정으로 넘어갔다.

| 구간 | USER | GDI |
|---|---|---|
| 메뉴를 한 번도 안 연 상태 | **31** | 48 |
| 메뉴 열린 순간 (41회 모두) | **44~46** (+13) | — |
| 첫 열기 이후 닫힌 상태 | **33~34** (+2~3, **일회성**) | 51 |
| 41회 여닫은 뒤 · 40초 유휴 | **34** (35에서 회수돼 안정) | 51 |

**판정** — 1차 7회 + 2차 34회 = **41회** 여닫는 동안 닫힌 값이 33~36 범위를 벗어나지 않았다. 서브메뉴 8개가 샌다면 41 × 9 ≈ **+370** 이어야 한다. 1차 종료 34 → 2차 시작 33 으로 **내려간 구간**도 있어 단조 증가가 아니다.

첫 열기의 **+3 은 누수가 아니다** — 누수의 정의는 「반복하면 쌓인다」인데 41회를 반복해도 그 자리다. Win32 가 팝업 메뉴를 처음 띄울 때 만드는 일회성 리소스로 보인다. 유휴 20초 뒤 35→34 로 내려간 것도 지연 회수가 동작한다는 신호다.

### 왜 이 방법이 되는가

- **HMENU 가 USER 오브젝트**라는 점이 핵심이다. `Process.HandleCount`(커널 핸들)로는 안 잡힌다 — 엉뚱한 계측기를 골랐으면 「안 늘었다」는 잘못된 안심을 얻었을 것이다.
- 누수 규모가 **회당 9개**라 표본이 적어도 감지된다. 7회만으로도 +63 이 보였어야 했고, 41회면 오차와 혼동될 여지가 없다.

### 3차 A 결함이 무엇인가

`Shell_NotifyIconW` 는 탐색기 응답을 기다리는 **블로킹 크로스프로세스 호출**이다. 그 대기 중에도 Windows 는 이 앱에 메시지를 밀어넣어(대표적으로 `WM_THEMECHANGED`) 아이콘 갱신 함수가 **자기 자신 안으로 재진입**한다. 앱은 재진입분을 버리지 않고 「보류 표식」에 적어 뒀다가 바깥 호출이 끝나면 반영하는데 —

> 보류를 **적어두는 곳은 둘**(`UpdateState` · `HandleAddRetryTimer`)인데 **꺼내 쓰는 곳은 `UpdateState` 하나뿐**이었다.

재시도 프레임에서 생긴 보류는 아무도 먹지 않고 사라진다 → 그 사이 바뀐 한/영·색이 영영 반영되지 않아 **트레이 아이콘이 실제 상태와 어긋난 채 남는다.** 수정은 셸 호출을 `Tray.RunShellCall` 단일 경로로 모은 것.

발동하려면 ① `NIM_ADD` 실패 → ② 재시도 타이머 → ③ 그 구간에 테마 변경 → ④ 보류 미소비. 08-03 관찰은 **①부터 일어나지 않았다**(재시도 0건).

1. 시작 지연 `PT15S` 가 **정확히 이 레이스를 피하려고** 들어 있다. [KoEnVue_PRD.md:214](../KoEnVue_PRD.md) — *"explorer 트레이가 초기화되기 전에 앱이 떠서 `NIM_ADD` 가 실패하는 레이스를 회피"*
2. 지연을 손으로 바꿔도 앱이 시작할 때 `<Delay>` 를 검사해 **자동 재등록**한다
