## 이번 검증에서 확인된 사실 (다음 실시자를 위한 것)

1. **config 감지는 5초 폴링이다.** 파일을 고치면 앱이 알아채기까지 **0~5초**가 걸린다(관측: 0.9초 · 1.4초 · 5.8초 간격). "5초 안에 하라"는 절차가 여럿 있는데, 실제 창은 그보다 **좁을 수도 넓을 수도** 있다 — E-1 참조.
2. **로그에 남지 않는 영역이 있다.** 아래 세 가지는 `koenvue.log` 를 뒤져도 나오지 않으므로 **눈으로 본 것이 유일한 근거**다.
   - **배지 표시** — `HideOverlay`(숨김)만 기록하고 표시 이벤트는 없다
   - **테마/강조색 변경** — `HandleSettingChange` 에 Logger 호출이 없다
   - **DPI 변경** — `HandleDpiChanged` 에 Logger 호출이 없다 (형제인 `HandleDisplayChange` 는 `Logger.Info("Display changed")` 가 있다)
3. **PowerShell 로 DPI 를 재면 틀린 값이 나온다.** PowerShell 은 DPI-unaware 프로세스라 모든 모니터가 96(100%)으로 보인다. `SetProcessDpiAwarenessContext(-4)` 를 먼저 호출해야 실제 배율이 나온다.
4. **관리자 권한 창의 한/영이 안 되는 것은 결함이 아니다.** 작업 관리자·레지스트리 편집기 등 High IL 창은 UIPI 로 막힌다(`asInvoker` 인 P5 규칙의 대가). 위치 추적(`PositionUpdated`)은 되고 IME 상태만 못 읽는다. `admin_elevation: true` 로 해소되는 것을 실기 확인했다 — [config-reference.md](../config-reference.md) 의 `admin_elevation` 설명에 이미 적혀 있는 내용이다.

## A. 5분 안에 끝나는 것 (재현이 쉽고 영향이 큼)

### A-1. 주석 있는 config 에서 커서 표시 방식이 유지되는가 — 3차 M 🔴 ✅

가장 재현하기 쉽고, 고치기 전에는 **거의 확실히 재현되던** 것.

1. 앱을 종료한다.
2. `config.json` 첫 줄 다음에 주석을 한 줄 넣는다: `// 테스트`
3. 같은 파일에서 `"cursor_display_mode": "soft"` → `"sharp"` 로 바꾼다.
4. 앱을 실행한다.
5. **트레이로 아무 값이나 바꾼다**(투명도 등) — 원래 버그는 이 저장 시점에 확정됐다.

**기대** — 커서 헤일로가 선명한(sharp) 모양으로 나온다. 트레이 저장 후에도 `config.json` 의 값이 `sharp` 그대로다.
**고치기 전** — 매번 `soft` 로 되돌아가고, 트레이를 한 번이라도 조작하면 파일에도 `soft` 가 확정됐다.

**2026-08-03 결과** — 통과. 부팅 후 파일 mtime 이 편집 시각 그대로였고(앱이 덮어쓰지 않음), 트레이로 투명도를 0.85→0.6 으로 바꾼 뒤에도 `sharp` 가 살아남았다. DEBUG 로그의 `Cursor halo config applied (… displayMode=Sharp …)` 가 런타임 측 독립 증거.

> **저장하면 주석은 사라진다.** 값은 지키지만 `//` 주석 자체는 JSON 직렬화가 보존하지 못한다. 버그가 아니다.

### A-2. 로그 설정이 즉시 반영되는가 — 3차 C 🔴 ✅

1. 앱 실행 → 트레이 우클릭 → 상세 설정.
2. 로그 수준을 `DEBUG` 로 바꾸고 「확인」.
3. `koenvue.log` 를 연다.

**기대** — 확인을 누른 직후부터 `[DEBUG]` 줄이 쌓인다.
**고치기 전** — 파일에는 저장되지만 앱을 다시 켤 때까지 `[DEBUG]` 가 한 줄도 안 나왔다.

**2026-08-03 결과** — 통과. 재시작 없이 즉시 기록됐고, 순서까지 맞았다 — `config applied`(09:59:37.551)가 `Config saved`(.553)보다 **2ms 먼저**다. Logger 가 다른 모듈과 같은 전이 경로를 탄다는 뜻.

### A-3. 지운 위치 기록이 그 자리에서 사라지는가 — 3차 F·Q 🟠 ✅

1. 아무 앱(예: 메모장)을 띄우고 배지를 다른 자리로 드래그한다.
2. 트레이 우클릭 → 위치 기록 정리 → 그 앱 항목을 선택해 삭제.
3. **메모장을 닫지 말고** 다시 포커스를 준다.

**기대** — 배지가 기본 위치로 돌아온다. `config.json` 의 `indicator_positions` 에서도 그 항목이 사라져 있다.
**고치기 전** — 창이 살아 있는 동안 옛 좌표를 계속 썼고(Q), 저장 시점에 파일이 바뀌어 있었다면 지운 항목이 파일에 되살아났다(F).

**2026-08-03 결과** — 통과. 로그가 전 과정을 찍었다: `Saved relative position for notepad++` → `Cleaned 1 position(s)` → `Config saved` → `PositionUpdated: … hwnd=0x702FA … saved=0`. 마지막 줄의 **hwnd 가 삭제 전과 동일**한 것이 Q 의 결정적 증거 — 창을 닫지 않았는데도 캐시가 무효화됐다.

## B. 트레이 아이콘 (3차 A·B, 2차 G7·G12)

### B-1. 부팅 직후 아이콘이 실제 한/영과 맞는가 — 3차 A 🔴 ◐ 부분 관찰

재현 조건이 까다롭다(부팅 재시도 구간 + 테마 변경이 겹쳐야 함). **실패해도 결론을 내리기 어려우니**, 아래를 관찰만 하고 이상하면 로그를 남긴다.

1. 트레이 우클릭 → 시작 프로그램 등록.
2. Windows 를 재시작하고 로그인.
3. 로그인 직후 트레이 아이콘과 실제 한/영 상태가 맞는지 본다. 한/영을 두어 번 눌러 본다.

**기대** — 아이콘이 항상 실제 상태를 따라간다.
**이상하면** — `koenvue.log` 에서 `NIM_ADD` 로 검색해 재시도가 있었는지 확인하고 그 구간을 보고.

**2026-08-03 관찰 (재부팅 1회, `d:\_portable\KoEnVue\koenvue.log`)** — **결함 없었음. 다만 수정 검증은 아니다.**

- 부팅 10:58:12 → 자동 시작 10:59:56(승격 자식) → **10:59:57.003 `Tray icon initialized`** 한 번에 성공
- 이후 9시간 20분 · 5,584줄에서 **WARN/ERROR 0건 · `retry` 0건 · `recreat` 0건**
- **재시도가 0건이라는 점이 판정의 핵심이다.** 3차 A 는 *`NIM_ADD` 재시도 구간에 테마 변경이 끼어드는* 레이스인데, 재시도 자체가 없었으니 **결함이 발동할 전제가 만들어지지 않았다.** 따라서 「실사용에서 문제 없었음」만 확인됐고 「수정이 그 레이스를 막는지」는 여전히 미확인이다 — 이 항목을 ✅ 로 올리려면 **재시도가 실제로 잡힌 부팅**이 필요하다.
- 부수 확인: `koenvue_crash.txt` 는 이름과 달리 크래시가 아니라 **승격(elevation) 진단**이 쌓이는 파일이다(정상 3줄). 파일명만 보고 크래시로 오인하기 쉽다.

### B-2. 탐색기 재시작 후 아이콘이 살아나는가 — 3차 B 🟠 ✅

1. 앱 실행 상태에서 작업 관리자 → Windows 탐색기 → 「다시 시작」.
2. 트레이를 본다.

**기대** — 아이콘이 다시 나타나고, 한/영을 누르면 정상 갱신된다.

**2026-08-03 결과** — 통과(2회). 로그: `TaskbarCreated broadcast received, recreating tray icon` → `Tray icon removed` → `Tray icon initialized` → `Tray icon recreated`.

> **📌 후속 과제 — 해결됨 (2026-08-03)** — 이 경로에서 매번 `[WARN] Failed to remove tray icon on shutdown` 이 찍혔다. 두 가지가 어긋나 있었다: ⓐ **종료 중이 아닌데 "on shutdown"** — 재생성 경로가 같은 `Remove` 를 공유한다, ⓑ **실패가 당연한 상황에 WARN** — 탐색기가 방금 죽어 아이콘을 지울 셸이 없다. `TrayRemoveReason`(종료·재생성·트레이 해제) 도입으로 정리했다.

>
> ```

> 20:34:07.633 [DEBUG] Tray icon delete skipped — no shell registration (Explorer restarted)
> 20:34:07.633 [INFO]  Tray icon removed (recreate)
> 20:34:07.760 [INFO]  Tray icon recreated (TaskbarCreated or recovery)

>
> **`[WARN] Failed to remove tray icon on shutdown` 이 소멸**했다. 그리고 이 확인은 **실패 분기가 발동한 상태**에서 이뤄졌다 — `Tray icon delete skipped` 가 찍혔다는 것은 `NIM_DELETE` 가 실제로 `false` 를 반환했다는 뜻이고, 성공했다면 그 줄 자체가 나오지 않는다.

## C. 창 lifecycle · 모달 (2차 G5·G10·G16·G17)

### C-1. 「관리자 권한」 토글 후 정상 종료되는가 — 2차 G5 🟠 ✅

1. 트레이 우클릭 → 관리자 권한 실행 토글 → UAC 승인.
2. 새로 뜬 인스턴스가 정상 동작하는지 본다(배지·트레이·한영 감지).
3. 종료한다.

**기대** — 좀비 트레이 아이콘이 남지 않고, 로그 끝에 `KoEnVue stopped` 가 있다.

**2026-08-03 결과** — 통과. 종료 시퀀스 한 덩어리에서 **세 가지가 동시에** 확인됐다:

```
09:38:25.527  OnProcessExit: threadId=1, mainThreadId=1, sameThread=True          ← G18 재현
09:38:25.581  Tray icon removed                                                    ← 좀비 방지
09:38:25.582  DestroyWindow(_hwndOverlay) ok
09:38:25.586  DestroyWindow(_hwndCursorOverlay) ok
09:38:25.586  DestroyWindow(_hwndMain) skipped: already reset by WM_DESTROY        ← G5

`_hwndMain` 만 `skipped` 이고 오버레이 둘은 `ok` — 트레이 토글이 보낸 `WM_CLOSE` 가 메인 창을 먼저 죽였고 `WM_DESTROY` 가 핸들을 즉시 내렸다는 뜻이다. G5 설계 그대로다.

### C-2. 설정 창을 닫은 뒤 배지가 돌아오는가 — 2차 G10 🟠 ✅

1. 트레이 우클릭 → 상세 설정 → 「확인」 또는 「취소」로 닫는다.
2. **아무 창도 클릭하지 말고** 기다린다.

**기대** — 배지가 곧 다시 나타난다.
**고치기 전** — 다른 창을 직접 클릭할 때까지 나타나지 않았다.

**2026-08-03 결과** — 통과(눈 확인). 배지 표시는 로그에 남지 않으므로 교차 확인 불가 — 위 「확인된 사실」 2 참조.

### C-3. 설정 창이 열려 있는 동안 배지가 잠기는가 — 2차 G16 🟠 ✅

1. 상세 설정을 연 채로 배지를 드래그해 본다.

**기대** — 움직이지 않는다.

**2026-08-03 결과** — 통과. 로그의 `ModalGate triggered HIDE: fgPid=…, ModalActive=True` 가 설정 창을 모달 대상으로 인식했다는 증거.

### C-4. 잘못된 config 안내가 한 번만 뜨는가 — 2차 G17 🟠 ✅

1. 앱 실행 중에 `config.json` 을 고의로 깨뜨린다(닫는 중괄호 하나 삭제).
2. 안내 창이 뜨면 **닫지 말고** 파일을 고쳐 저장한다. **깨진 상태로 한 번 더 저장해 보면** 더 정확하다 — 원래 버그는 *박스가 떠 있는 동안 파일이 바뀔 때마다* 쌓이는 것이었다.
3. 박스를 닫고, 고친 값이 반영되는지 본다.

**기대** — 안내 창이 늘어나지 않는다. 창을 닫으면 고친 설정이 반영된다.

**2026-08-03 결과** — 통과. 파일을 **세 번** 건드리는 동안 `#32770`(MessageBox) 창은 계속 1개였다(창 열거로 확인). 깨져 있던 58초 동안 `Config saved` 가 한 번도 없어 **앱이 깨진 파일을 덮어쓰지 않았다**. 박스를 닫는 순간 `Config loaded` → `Config reloaded` 가 찍혔고, 그 사이 바꿔 둔 `label_width` 60 이 적용돼 **배지 창 크기가 59×48 → 120×48** 로 바뀌었다(= `label_width` 60 × `indicator_scale` 2).

```

09:16:30.612  Config loaded from …config.json      ← 박스 닫는 순간
09:16:30.614  Config reloaded
```

> **안내 박스가 다른 창에 가려진다.** 실시 중 박스를 찾기 어려웠다. Alt+Tab 으로 「KoEnVue」를 고르면 앞으로 나온다. 창 좌표는 `GetWindowRect` 로 확인 가능(관측: 420×179).

## D. 배지 표시 (2차 G4·G14·G15·G19, 3차 J)

### D-1. 파일로 배지 숨김을 해제하면 나타나는가 — 2차 G19 🟠 ✅

1. 트레이 좌클릭으로 배지를 숨긴다. 좌클릭은 `Both → BadgeOnly → CursorOnly → None → Both` 로 순환하므로 **배지가 사라지는 상태**(`CursorOnly` 또는 `None`)까지 누른다.
2. 편집기에서 `config.json` 의 `"user_hidden": true` → `false` 로 바꾸고 저장.
3. **편집기에 포커스를 둔 채** 기다린다(최대 5초).

**기대** — 배지가 나타난다.

**2026-08-03 결과** — 통과. `Config loaded` → `Config reloaded` 후 배지 오버레이 창이 다시 가시 상태(`59×48`)가 됐다 — 직전 `None` 상태에서는 가시 창이 0개였다. 눈 확인도 받았다.

### D-2. 모니터 간 이동·절전 복귀 후 배지가 남는가 — 2차 G15 🟠 ✅ (절전 복귀는 미실시)

창을 다른 배율의 모니터로 옮기거나 절전 후 복귀했을 때 배지가 사라지지 않아야 한다.

> **환경 조건** — 이 항목은 **배율이 서로 다른 모니터가 있어야** 성립한다. 모든 모니터가 같은 배율이면 `WM_DPICHANGED` 가 아예 발생하지 않아 G15 경로를 타지 않는다. 배율 확인은 「확인된 사실」 3 참조.

**2026-08-03 결과** — 모니터 이동은 통과. 검증 환경은 150%(2560×1600) + 100%(3440×1440). 로그에 모니터 왕복이 4회 남았고(음수 X 좌표 = 150% 모니터), 그중 셋은 1초 이내의 빠른 전환이었다. 경계에서 `Position clamped` 도 정상. **절전 복귀는 미실시.**

### D-3. 강조색 변경 시 커서 헤일로 색도 바뀌는가 — 2차 G9 🟠 ✅

> **⚠️ 절차 정정 (2026-08-03)** — 이전 판은 "라이트↔다크를 전환한다"라고 적었는데 **틀렸다.** `theme: system` 이 따라가는 것은 라이트/다크 모드가 **아니라 강조색(accent color)** 이다([ThemePresets.cs:112](../../App/Config/ThemePresets.cs) — `DwmGetColorizationColor` → `HangulBg`, 그 보색 → `EnglishBg`). 라이트↔다크를 아무리 전환해도 강조색은 그대로라 **아무 일도 일어나지 않고, 통과인지 실패인지 구분조차 되지 않는다.** 실제로 이 오류 때문에 한 차례 오판할 뻔했다.

1. `theme` 을 `system` 으로 둔다.
2. Windows 설정 → 개인 설정 → **색 → 강조색**을 다른 색으로 바꾼다(「자동」이면 「수동」으로 먼저 바꾼다).
3. 배지·트레이뿐 아니라 **커서 헤일로**도 새 색이어야 한다.

**2026-08-03 결과** — 통과. 강조색 `#0078D4` → `#0063B1` 변경(레지스트리 `HKCU:\SOFTWARE\Microsoft\Windows\DWM\AccentColor` 로 확인)에 **셋이 함께** 따라갔다. 수정 코드는 [Program.SystemEvents.cs:82](../../Program.SystemEvents.cs) 의 `ApplyCursorConfigChange()` 호출.

> `theme: system` 은 색을 **런타임에만 계산**하고 `config.json` 의 사용자 색은 덮어쓰지 않는다. `custom` 으로 되돌리면 원래 색이 그대로 돌아온다.

### D-4. 드래그 중 배지가 따라오는가 — 3차 J 🟡 ✅

창을 잡고 끄는 동안 배지가 옛 자리에 남지 않고, 놓으면 새 위치에 나타나야 한다. (재현이 산발적 — 이상할 때만 기록)

**2026-08-03 결과** — 통과. 천천히·빠르게·모니터 간 이동 세 가지 모두 이상 없음.

### D-5. 일본어·중국어 IME 에서 로그가 조용한가 — 2차 G4 🟠 ⬜ 미실시

해당 IME 를 쓸 때 `koenvue.log` 에 `HIDE` 류가 반복되지 않아야 한다.

> 해당 IME 가 설치돼 있어야 한다. 2026-08-03 실시분에서는 건너뛰었다.

## E. 설정 저장 (2차 G6·G11, 3차 E)

### E-1. 파일 편집과 트레이 조작이 겹쳐도 둘 다 살아남는가 — 2차 G6 🔴 ✅

1. `config.json` 에서 `cursor_indicator_enabled` 를 `false` 로 바꾸고 저장.
2. **앱이 그 변경을 알아채기 전에** 트레이 우클릭 → 투명도를 **지금과 다른 값**으로 바꾼다.

**기대** — 헤일로가 사라지고(파일 편집 반영) 투명도도 바뀐다(트레이 조작 반영). `config.json` 에 둘 다 들어 있다.

> **⚠️ 타이밍 (2026-08-03 실측)** — 이 항목은 **손으로 맞추기 어렵다.** 병합 조건은 "디스크가 앱이 마지막으로 본 상태에서 벗어났을 때"([JsonSettingsManager.cs:250](../../Core/Config/JsonSettingsManager.cs))인데, 앱이 그것을 **0~5초 안에** 알아채고 기준선을 갱신해 버리면 병합 대상이 아니게 된다. 실제로 두 번 놓쳤다(0.885초·1.4초 만에 감지).
>
> **통한 방법** — 파일의 `cursor_indicator_enabled` 를 **0.6초 간격으로 true↔false 토글**하며 30초 이상 유지하면, 5초 폴링이 따라오지 못해 **병합 창이 계속 열려 있다.** 그동안 아무 때나 트레이를 조작하면 된다. 마지막에 원하는 값으로 고정하고 토글을 멈춘다.
>
> **판정은 로그로** — 병합이 일어나면 `Config merged with on-disk edits during save; applying merged state` 가 찍힌다. 이 줄이 없으면 창을 놓친 것이므로 결과가 무엇이든 검증이 성립하지 않는다.

**2026-08-03 결과** — 통과. 병합 시퀀스가 그대로 남았다:

```
09:52:50.445  Config changed on disk since last sync; merged only the fields this save touched
09:52:50.446  Config saved
09:52:50.456  Config loaded                                              ← 되읽기
09:52:50.456  Config merged with on-disk edits during save; applying merged state
09:52:50.456  CursorOverlay disposed                                     ← 병합 결과가 즉시 적용됨
```

`applying merged state` **바로 다음 줄**이 `CursorOverlay disposed` 인 것이 G6 의 핵심 — 파일에서 온 「헤일로 끄기」가 병합 직후 실제로 적용됐다. 고치기 전에는 병합만 하고 적용하지 않아 다음 저장이 되돌렸다. 최종 상태는 `opacity: 0.95`(앱이 바꾼 값이 이김) + `cursor_indicator_enabled: false`(디스크 값이 이김) — 병합 규칙대로다.

### E-2. 설정이 통째로 초기화되지 않는가 — 3차 E 🔴 ⬜ 미실시

의도적 재현은 어렵다(저장 직후 찰나에 파일이 사라져야 함). **대신 평소 사용 중 색·위치가 갑자기 기본값으로 돌아가는 일이 있는지** 관찰한다. 그런 일이 생기면 `koenvue.log` 에서 `Config not found` 를 검색해 보고.

## F. 로깅 (2차 G1·G2·G3, 3차 D)

### F-1. 로그를 끄면 메모리가 늘지 않는가 — 2차 G1 🟠 ⬜ 미실시

1. `log_level: DEBUG` + `log_to_file: true` 로 10분쯤 실행.
2. `log_to_file` 을 `false` 로 바꾸고 저장.
3. 작업 관리자에서 메모리 사용량을 30분쯤 지켜본다.

**기대** — 계속 늘지 않는다.

### F-2. 로그를 다시 켜면 시각이 순서대로인가 — 3차 D 🟠 ⬜ 미실시

F-1 뒤에 `log_to_file` 을 다시 `true` 로 바꾸고 `koenvue.log` 를 연다.

**기대** — 기록 시각이 뒤로 뛰지 않는다(옛 줄이 한꺼번에 쏟아지지 않음).
