### 기각 판정의 근거

- **P ❌ 오탐** — `StopDrainThread` 의 `FlushQueueLocked`(:574)가 `TryReopenWriter` 로 파일을 다시 여는 것은 **잔여 flush 라는 의도된 동작**이다. 로깅을 끄기 직전까지 큐에 쌓인 줄을 마저 쓰기 위한 것이고, 바로 뒤 :576 에서 Dispose 한다. "로깅을 껐는데 파일이 열린다" 는 서술은 순서를 뒤집어 읽은 것이다.
- **K ⚠️ 부분 오탐** — `RunExternal` 이 `EnableWindow` 를 하지 않는 것은 **주석에 명시된 설계**다(:178-183 "Run 과 달리 메시지 펌프나 EnableWindow 는 건드리지 않으며"). 배지가 `MessageBoxW` 뒤에서 드래그되는 것 자체는 성립하지만, G16 의 핵심 피해("「확인」이 커밋 베이스로 되돌린다")는 안내 박스에 커밋 베이스가 없으므로 성립하지 않는다. 남는 것은 UX 이슈뿐이라 심각도를 낮춘다.
- **H ⚠️ 피해 낮음** — 가드가 없는 것은 사실이다(9곳 전부 확인). 그러나 필드가 `IntPtr.Zero` 로 내려간 뒤의 `PostMessageW(Zero, …)` 는 **그냥 실패**할 뿐 위험하지 않다. 실제 재활용 위험은 그룹 **G**(옛 유효 HWND 를 든 사본) 쪽이다. 문서의 논거 문장이 부정확한 것이 본질이라 G 와 함께 다룬다.

## 4. 수정 기록

### 묶음 1 — 트레이 셸 호출 프로토콜 (A·B) ✅

**뿌리 하나** — `_shellCallInProgress` 가드와 보류 표식(`_updatePending`/`_pendingUpdateState`/`_pendingUpdateConfig`)이 **한 쌍인데 흩어져 있었다.** 가드를 세우는 곳은 둘(`UpdateState`·`HandleAddRetryTimer`)인데 소비·정리하는 곳은 `UpdateState` 하나뿐이었고, 같은 블로킹 `Shell_NotifyIconW` 를 부르는 `Initialize`·`Remove` 는 가드 자체가 없었다.

셸 호출 구간을 **`Tray.RunShellCall(Action, bool drainPending)` 단일 진입점**으로 모았다 (P4). 설계 요점 셋:

- **최외곽 프레임만 가드를 되돌린다** — 중첩 호출의 `finally` 가 바깥 구간의 가드를 먼저 내리면 그 구간의 재진입이 다시 열린다. `ModalDialogLoop.RunExternal` 과 같은 스택형 복원.
- **`Remove` 만 `drainPending: false`** — 제거 중에 보류분을 재생하면 방금 지운 아이콘을 되살리고, 그 시점 `_currentIcon`·`_notifyIcon` 은 이미 정리된 뒤다. **다만 표식을 지우지도 않는다** — `Recreate` 가 Remove 직후 Initialize 를 부르므로, 제거 구간에 들어온 더 새로운 상태는 그 Initialize 의 드레인이 소비해야 한다.
- **`_initialized` 전이를 셸 호출 밖으로** — `Initialize` 는 NIM_ADD **전**에 true 로(그래야 그 구간의 재진입이 조용히 사라지지 않고 보류로 남는다), `Remove` 는 NIM_DELETE **전**에 false 로(그래야 재진입이 첫 줄에서 돌아가 방금 넘긴 HICON 을 만지지 않는다).

**검증** — `WindowLifecycleTests` 2건 추가 (226 → **228**). 둘 다 **대조군 실측**: `outermost` 판정을 제거하니 중첩 테스트가, 표식 정리를 무조건으로 되돌리니 제거-구간 테스트가 정확히 실패했다. 셸/GDI 미접촉으로 검증된다(`_notifyIcon = null` + `_hwndMain = Zero`). **재시도 프레임이 보류를 실제로 소비하는지**는 `UpdateStateCore` 가 GDI 에 닿아 단위 테스트로 고정할 수 없다 — 구조가 `RunShellCall` 단일 경로라는 사실로만 담보된다.

### 묶음 2 — 전이 적용 통합 + 설정 전멸 재봉쇄 (C·E) ✅

**C — 적용자 나열에서 Logger 만 빠져 있었다.** `HandleMenuCommand` 의 `updateConfig` 람다가 프로필 캐시·I18n·감지 방식·오버레이·커서 헤일로·UserHidden·트레이 전이를 **하나씩 나열**해 적용했는데, 그 목록에 로거가 없었다. 그래서 상세 설정 창에서 `log_level`·`log_to_file` 을 바꾸면 디스크에는 저장되지만 러닝 로거는 그대로였고, `Settings.Save` 의 mtime self-bump 가 핫리로드까지 막아 **재시작 전까지** 반영되지 않았다. `SaveAndSync` 는 3-way 병합이 실제로 일어난 경우에만 `ApplyConfigTransition` 을 부르므로 그쪽으로도 구제되지 않는다.

G6 이 "개별 호출자를 고치는 대신 진입점을 하나로 모은다" 고 적은 함정이 **이 자리에서 실제로 터진 것**이라, 나열을 통째로 걷어내고 람다도 `ApplyConfigTransition(prev, _config)` 을 쓰게 했다. 두 경로의 유일한 실질 차이였던 「포그라운드 hwnd 를 모를 때 색만 갱신」은 `RefreshVisibleIndicator` 에 흡수해 세 경로가 같은 헬퍼를 지나가게 했다(P4).

**E — `TryLoad` 의 파일 부재 분기가 `true` 를 돌려주고 있었다.** AUDIT-2026-07-30 §G 는 "파싱 실패 시 전 필드 디폴트를 디스크에 확정 → 사용자 설정 전멸" 을 `TryLoad` 의 **false 반환**으로 닫았는데, **파일 부재 분기는 그 가드 밖에 있었다** — `new T()` 를 만들어 `Save` 로 디스크에 쓰고 `true` 를 돌려준다. 호출자에겐 정상 로드로 보이므로 §G 가드가 발동하지 않는다.

진입점이 둘이다. ① `Save` 가 병합 후 되읽는 순간 파일이 사라져 있으면(백신 격리·동기화 클라이언트) 디폴트를 호출자에게 돌려주고, `SaveAndSync` 가 그것을 `_config` 에 실은 뒤 `ApplyConfigTransition` 까지 돌려 **디폴트를 앱 전역에 적용**한다. ② 핫리로드의 `Settings.TryLoad` 도 같은 분기에서 true+디폴트를 받는다.

**생성 책임을 `Load` 로 옮겼다** — 파일 부재 시 디폴트를 만드는 것은 "비교할 기존 인스턴스가 없는" 부팅 경로에서만 옳다. `TryLoad` 는 이제 파일이 없으면 **false + 디스크 미변경**이고, 런타임 호출자는 들고 있던 인스턴스를 유지한다.

**검증** — 테스트 228 → **229**. 기존 `TryLoad_파일이_없으면_true_이고_디폴트를_생성한다` 는 **옛 계약을 고정하던 테스트이고 그 계약이 곧 결함**이었다 — 새 계약 2건(`TryLoad` 는 false + 미변경 / `Load` 는 생성)으로 교체했다. C 는 구조적 사실이라 [conventions.md](../conventions.md) invariant 2줄로 고정: `ApplyConfigTransition(` = **4**(정의 1 + 호출 3), `Logger.(SetLevel|Initialize)(` in Program.cs = **4**(부팅 2 + 전이 함수 2 — 호출자가 자체 나열로 되돌아가면 이 카운트는 그대로면서 그 경로만 조용히 빠진다).

### 묶음 3 — Logger 전이 구간 배수 (D) ✅ / O 감수

**D — `PreInit` 이 부팅 1회 상태가 아니라 재진입 가능한 전이 상태가 된 것이 뿌리다.** `StopDrainThread` 는 `_route` 를 `PreInit` 로 되돌린 뒤 Join(최대 3s) + writer 락 대기(최대 1s)를 지난다. 그 ~4초 동안 다른 스레드(감지 루프는 80ms 주기)가 낸 로그는 `_preInitBuffer` 로 들어가는데, 최종 flush 는 `_logQueue` 만 비웠고 곧이어 `Drop` 이 확정되면 **아무도 비우지 않았다** — G1 이 닫은 트레드밀이 전이 구간의 잔여분으로 되살아나는 형태다. 나중에 로깅을 다시 켜면 그 묵은 줄이 신규 로그보다 앞에 쏟아져 타임스탬프가 과거로 점프하고, 켜지 않으면 프로세스 수명 내내 상주한다.

**이중 방어로 닫았다.** ① `StopDrainThread` 가 락을 잡은 정상 경로에서는 `FlushPreInitBuffer()` 를 최종 flush **앞**에 불러 갇힌 줄을 **파일까지 배수**한다(유실 자체가 없다). ② 락을 잡지 못한 경로를 위해 `RouteToDrop()` 헬퍼를 만들어 `Drop` 확정 4곳이 남은 버퍼를 비우고 드롭 수를 `Trace` breadcrumb 으로 남기게 했다(파일 로깅이 꺼진 상태라 파일에는 쓸 수 없다).

**검증 — 대조군 해석에 주의가 필요했다.** `LoggerReinitTests` 1건 추가(229 → **230**). 처음 두 번의 대조군은 **통과했다** — 한쪽 수정만 되돌리면 나머지 하나가 결과를 보장하기 때문이다. **둘을 모두 되돌렸을 때 비로소 실패**했다. 즉 이 테스트가 고정하는 것은 "`Drop` 확정 시점에 버퍼가 비어 있다" 는 **결과**이지 특정 구현이 아니다. 락 실패 경로 자체는 3초 이상 걸리는 파일 잠금이 필요해 단위 테스트로 만들 수 없으므로, 갇힌 줄을 버퍼에 직접 넣어 결과만 고정한다.

**O — 감수한다 (수정 없음).** `StopDrainThread` 가 writer 락 획득에 실패하면 `_fileWriter` 를 **의도적으로 건드리지 않고** 물러나는데(강제 Dispose·null 대입 둘 다 좀비의 다음 쓰기를 필터 밖 예외로 만들어 프로세스를 종료시킨다 — 릴리즈 리뷰 #4·#8·#11), `enabled=false` 경로는 그 뒤 곧바로 조기 반환하므로 "이후 Initialize 가 writer 를 정상 교체한다" 는 기존 논리가 성립하지 않는다. 남는 피해는 **파일 핸들 1개가 GC 까지 열려 있는 것**뿐이고, 좀비는 세대 가드에 막혀 쓰지 못하며 `SafeHandle` 파이널라이저가 회수한다. 이를 없애려는 수정은 위 세 결함을 되살릴 위험이 크다.

### 묶음 4 — 병합의 키 삭제 전파 (F) ✅

**disk-only 보존 규칙이 열린 딕셔너리 안쪽까지 내려간 것이 뿌리다.** 릴리즈 리뷰 #12 로 중첩 객체가 스칼라 단위까지 재귀하게 되면서(형제 키 유실을 막기 위한 옳은 수정이었다), 「디스크에만 있는 키는 보존한다」 는 루프가 `indicator_positions` · `indicator_positions_relative` · `app_profiles` **내부의 개별 항목**에도 적용됐다. 그 셋은 `Dictionary<…>` 라 JSON 상 Object 이고, 사용자와 앱이 **함께 키를 늘리고 줄이는** 곳이다. 무조건 보존하면 앱의 삭제(위치 기록 정리·프로필 삭제)가 디스크에 전파되지 않아 지운 항목이 다음 로드로 되살아난다.

**판정 기준을 기준선으로 삼았다** — base 에 있었는데 next 에 없으면 **앱이 이번에 지운 것**이므로 되살리지 않고, base 에도 없으면 사용자가 파일에 직접 넣고 앱이 아직 읽지 않은 것이므로 보존한다. 스키마 필드는 `nextObj` 에 항상 존재하므로 이 루프에 도달하지 않는다 — 영향은 열린 딕셔너리에 한정된다.

**검증** — `SaveMergeTests` 2건 추가 (230 → **232**). 삭제 전파와 **그 반대편**(사용자가 파일에만 넣은 프로필 보존)을 함께 고정했다 — 이 구분이 무너지면 둘 중 하나가 반드시 깨지기 때문이다. **대조군 실측**: 기준선 검사를 제거하니 삭제 전파 테스트가 정확히 실패했다.

### 묶음 5 — 마이그레이션 관용도 + 이동 래치 (M·J) ✅ / G·H·I·L 판정

**M — 마이그레이션만 다른 관용도로 읽고 있었다.** `PostDeserializeFixup` 은 **매 로드마다** 원본 config.json 을 두 번째로 열어 레거시 키를 판정하는데(병합본에는 디폴트가 섞여 부정확하므로 원본이 맞다), 그 `JsonDocument.Parse` 가 **기본 옵션**이었다. 이 프로젝트는 주석과 트레일링 콤마를 정상으로 취급하는데(`AppConfigJsonContext` · Core 양쪽 모두) 여기만 그것을 파싱 실패로 처리했고, 실패 시 `Soft` + `true` 를 돌려줘 **사용자의 `cursor_display_mode` 를 덮어썼다.** 결과적으로 **주석을 쓴 사용자가 `sharp`/`motion` 을 지정하면 매 로드마다 `soft` 로 되돌아가고, 다음 저장이 그것을 디스크에 확정**했다.

두 곳을 고쳤다 — ① 파싱 옵션을 정규 로드와 일치시키고 ② 읽지 못하면 `false` 를 돌려 **덮어쓰지 않는다**(읽을 수 없는 파일은 판정의 근거가 될 수 없다).

**J — 래치 하나가 두 의미를 겸했다.** `WindowMoving` 이 「이동 중」과 「HIDE 를 이미 보냈다」를 겸했는데, `IsIndicatorVisible()` 은 배지가 화면에 올라오는 동안 아직 false 다 — G4 이후 그 플래그는 `Animation.TriggerShow` 가 **반환한 뒤에** 대입되기 때문이다. 그 찰나에 이동을 처음 관측하면 HIDE 를 건너뛴 채 래치만 서고, 다음 틱부터는 `!WindowMoving` 이 false 라 **재시도 자체가 사라져** 드래그 내내 배지가 옛 좌표에 남았다. `HideSentForMove` 를 분리해 실제로 보낸 경우에만 래치가 서게 했다(해제 지점 3곳 모두 함께 리셋).

**검증** — 테스트 232 → **234**(M 2건: 주석 있는 레거시 파일 마이그레이션 · 읽기 실패 시 미덮어쓰기). **대조군 실측**: 파싱 옵션을 기본으로 되돌리니 마이그레이션 테스트가 정확히 실패했다. **J 는 단위 테스트가 불가능하다** — `PositionMode.Window` + `rectChanged` 경로는 `Dwmapi.TryGetVisibleFrame` 이 실제 창을 요구한다(기존 G14 테스트가 Win32 미접촉으로 검증되는 것은 모드 가드가 그보다 **앞**이기 때문이다).

**G·H — 감수 (수정 없음).** `_hwndMain` 의 모듈별 사본(`ImeStatus` · `Tray` · 애니메이터 2종)이 `WM_DESTROY` 에서 리셋되지 않는 것과, 감지 스레드의 `PostMessageW` 9곳에 Zero 가드가 없는 것은 **둘 다 사실이다**. 그러나 실질 피해가 낮다 — 필드가 Zero 로 내려간 뒤의 `PostMessageW(Zero, …)` 는 그냥 실패하고, 사본이 옛 HWND 를 드는 구간은 창 파괴부터 프로세스 종료까지의 짧은 창이라 커널이 그 값을 재발급할 여지가 거의 없다. 수정하려면 5개 모듈에 무효화 진입점을 배선해야 하는데(Core 쪽 둘은 App 을 참조할 수 없어 콜백이 필요하다), **이 세션이 이미 7개 그룹을 고친 상황에서 그 범위의 리팩터는 새 결함을 만들 위험이 이득보다 크다.** 문서의 "다른 스레드가 즉시 Zero 를 관측하고 자기 가드에 걸린다" 는 서술이 감지 스레드 쪽에는 구현돼 있지 않다는 사실만 여기 남긴다.

**I — 감수.** `Process.Dispose` 가 리다이렉트 파이프를 결정적으로 닫지 않는 것은 맞지만, `ReadToEndAsync` 가 EOF 에 도달한 뒤 `StreamReader` 파이널라이저가 회수한다. "매 우클릭마다 쌓인다" 는 GC 전까지만 참이다.

**L — ❌ 오탐.** 부팅 경로(`MainImpl` 9e)가 `EnableCursorOverlay()` 를 게이트 없이 부르는 것은 사실이나, `MainImpl` 은 프로세스당 **1회**만 실행되고 그 시점 `_hwndCursorOverlay` 는 `IntPtr.Zero` 다. 현 코드에 이중 생성 경로가 없다.

### 묶음 6 — mtime 스탬프 시점 + 세션 위치 캐시 무효화 (N·Q) ✅

**N — 스탬프를 내용보다 늦게 찍고 있었다.** `TryLoad` 는 파일 내용을 먼저 읽고, `JsonDocument` 2회 파싱 · 역직렬화 · `PostDeserializeFixup`(원본 파일 재개봉) · `Migrate` · `Validate` 를 다 지난 **뒤에** mtime 을 조회해 "이 내용과 동기화됨" 으로 확정했다. 그 창에 저장된 편집은 **새 mtime 이 옛 내용에 붙는** 결과가 되어 폴링이 더는 차이를 보지 못하고 영영 놓친다. 읽기 **전**에 찍은 값을 쓰도록 바꿨다 — 오차가 "다음 폴링이 같은 내용을 한 번 더 읽는다" 는 무해한 쪽으로 기운다.

**Q — 세션 캐시에 config 변경 무효화가 없었다.** `_hwndPositions` 는 드래그로만 채워지고 정리 경로가 죽은 창 · HWND 재활용 · 상한뿐인데, `GetAppPositionFixed` 는 이 캐시를 **1순위**로 조회한다. 그래서 위치 기록 정리 창에서 항목을 지우거나 파일에서 좌표를 고쳐도 **그 창이 살아 있는 동안에는** 옛 좌표가 계속 쓰였다(창을 닫았다 열면 새 HWND 라 저절로 풀려, 재현이 산발적이다).

**통째로 비우지 않는다** — 드래그로 만든 세션 위치는 아직 config 에 없을 수 있고, 무관한 리로드가 그것을 지우면 사용자가 방금 옮긴 배지가 되돌아간다. `prev`/`next` 를 프로세스명 단위로 비교해 **실제로 달라진 항목의 엔트리만** 버린다.

**검증** — `WindowLifecycleTests` 1건 추가 (234 → **235**). 삭제 전파와 「config 에 없던 세션 전용 위치는 유지」를 함께 본다. **대조군 실측**: 변경 판정을 항상 "그대로" 로 만드니 정확히 실패했다. **첫 대조군은 잘못 잡았다** — `ApplyConfigTransition` 쪽 호출을 지웠는데, 테스트가 그 함수를 리플렉션으로 **직접** 부르므로 통과했다. 「함수가 하는 일」과 「그 함수가 실제로 불리는가」는 다른 문제라, 후자는 [conventions.md](../conventions.md) invariant(`InvalidateSessionPositions(` = 2)로 따로 고정했다. **N 은 단위 테스트가 불가능하다** — 파이프라인이 도는 도중에 파일을 바꿔야 한다.

### R 재판정 — ⚠️ **부분 오탐**

"`SaveAndSync` 가 `ApplyConfigTransition` 을 부르면 `Logger.Initialize` 가 UI 를 5초 붙잡는다" 는 조건부로만 참이다. `ApplyConfigTransition`(Program.cs:1035-1037)은 **로그 관련 설정이 실제로 바뀐 경우에만** 재초기화한다 — 무변경 저장은 `Logger.SetLevel` 만 지난다. 남는 것은 "로그 설정을 바꾼 저장에서 UI 가 잠시 멈춘다" 인데, 그것은 기존 핫리로드 경로에도 동일하게 있던 성질이고 재초기화가 실제로 필요한 경우다. **C 를 고치는 데 제약이 되지 않는다.**
