규범 문서(리뷰 규칙·게이트 정의)에서 **"전부 0" / "모두 X" 류 일괄 서술**을 발견하면 (1) 그 블록 안에 예외가 있는지 먼저 실측하고 (2) 고칠 때는 그 문구의 **파생 사본을 하네스 전체에서 전수 grep** 한 뒤 함께 정정한다. 원본 한 곳만 고치면 사본이 계속 오판을 만든다. [[verify-load-bearing-claims]] 가 정량 주장을 재현하는 쪽이라면, 이쪽은 **일괄 주장(전칭 명제)의 반례를 찾는** 쪽이다.

**Why:** 2026-07-27 `/release-review` 가 `docs/conventions.md` 의 P6 invariant 블록 헤더 "All must return **0 matches**" 를 결함으로 확정했다. 같은 블록 21개 grep 중 **9개가 의도적으로 0 이 아닌 기대값**(1+ / ≥1 / 3 / 4)을 인라인 주석에 갖고 있었다 — 헤더가 자기 블록 본문에 9번 반박되는 상태. 실측하니 위반은 0건이었고, 진짜 위험은 **정상 통과 항목을 위반으로 오판해 릴리즈를 잘못 막는 것**이었다. 더 중요한 건 전파였다: 원본 3곳(헤더·PR-15 서술 "각 1매치"·Testing 절 요약) 외에 `.claude/agents/reviewer.md` 3곳과 **`.claude/hooks/session-start.ps1:146` — 매 세션 시작마다 "모두 0건이어야 합니다" 를 주입하던 경로**까지 총 6곳이었다. 원본만 고쳤다면 hook 이 매 세션 오해를 되살렸다.

**규모 증거 (2026-07-27 후속 전수 점검):** 원본 6곳을 고친 뒤 하네스 전 구역(agents·skills·workflows·hooks·CLAUDE.md·harness.md·memory)을 서브에이전트 5명으로 전수 점검하니 **같은 계열이 44곳 더** 나왔다. 그중 하나는 문구가 아니라 실동작 버그였고(`session-start.ps1` 헤더 정규식이 `session-end` 블록을 영구 누락), 하나는 하네스 개선 워크플로우가 폐기 정책을 기준으로 삼아 **올바른 설정을 위반으로 오탐**하게 만들고 있었다. 교훈: 사본은 "몇 곳" 이 아니라 "구역 전체" 단위로 퍼진다 — 부분 grep 으로 끝내면 반드시 남는다. 실제로 이 세션에서 내가 `reviewer.md` 를 고치며 세 번째 사본인 `harness.md` 를 빠뜨렸다.

**How to apply:** 기대값의 단일 진실원은 **각 grep 줄의 우측 `#` 주석**(없으면 0 매치)이며, 문서 산문·에이전트 정의·hook 문구는 전부 사본이다. 사본 탐색은 결론 문구(`0건`, `0 matches`, `모두 0`)로 `.claude/` + `docs/` 전수 grep. 리뷰 게이트 문서를 고친 뒤엔 **grep 을 전수 실측해 정정된 서술이 실제와 맞는지 확인**한다(주장만 바꾸고 검증 안 하면 같은 실수 반복). 덧붙여 — 이 결함은 리뷰 워크플로우가 **자기 리뷰 규칙에서** 찾아냈다: 하네스 자체도 리뷰 대상 범위에 든다.
