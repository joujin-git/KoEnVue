**부정적 관측을 결론으로 확정하기 전에 계측기를 먼저 검증한다.** "로그에 없다" · "값이 같다" · "한 번 해보니 안 된다" 는 셋 다 대상이 아니라 **측정 쪽 결함**일 수 있다. [[tool-limit-verify-first]] 가 "감수 전에 찔러본다" 라면 이건 "부정 결론 전에 계측을 의심한다".

**Why:** 2026-08-03 실기 검증 한 세션에서 같은 뿌리로 세 번 오판 직전까지 갔다. (1) **로그 부재 → 동작 부재로 읽을 뻔** — 배지 표시·테마 변경·DPI 변경은 Logger 호출이 **아예 없는** 영역이라 무로그가 정상이다. 코드를 열고서야 갈렸다. (2) **측정 도구의 전제 미확인** — PowerShell 이 DPI-unaware 라 `GetDpiForMonitor` 가 두 모니터를 다 96(100%)으로 보고했고, 그 값을 근거로 "배율이 같아 D-2 재현 불가"라고 사용자에게 보고했다. 실제로는 150%+100% 였다(`SetProcessDpiAwarenessContext(-4)` 선행 필요). 사용자가 "150%, 100% 인데" 라고 정정했다. (3) **한 방법의 실패를 항목의 불가능으로 확대** — E-1 병합 창이 0~5초라 두 번 놓치자 "실기 재현 불가"로 결론지었는데, 사용자의 "다시 테스트해" 에 방법을 바꾸니(0.6초 간격 토글로 창을 30초 유지) 성립했다.

**How to apply:** 부정 결론을 내기 전에 두 가지를 한다 — ⓐ **계측기가 그 사건을 잡을 수 있는지 확인**한다(로그라면 해당 경로에 Logger 호출이 있는지 grep, 측정 API 라면 프로세스 전제가 맞는지). ⓑ **양성 대조군을 만든다** — 반드시 일어나는 조건을 걸어 계측이 실제로 반응하는지 본다. 확인이 안 되면 "안 일어났다" 가 아니라 **"이 방법으로는 확인할 수 없다"** 로 보고한다. 둘은 사용자에게 전혀 다른 정보다.
